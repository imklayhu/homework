# 视频理解进度日志设计

## 目标

长视频分析期间，在任务页面持续展示用户可理解的处理进度和最近日志。状态需要持久化，刷新页面后仍可恢复；日志不得暴露模型地址、密钥、原始响应或异常堆栈。

## 产品形态

“理解视频内容”步骤在进行中时展开为进度面板，包含：

- 总体百分比；
- 当前片段与总片段数，例如“第 3/15 个片段”；
- 当前片段的时间范围，例如“01:00–01:30”；
- 当前动作：生成分析片段、等待模型理解、片段完成、模型重试；
- 最近 20 条用户友好型日志，包含时间、级别和消息。

完成时显示 100%。失败时保留此前日志，并显示失败发生在哪个片段和阶段。尚未进入视频理解阶段时不展示空日志面板。

## 数据模型

在分析任务上保存进度快照：

- `progress_current`：已完成的片段数；
- `progress_total`：总片段数；
- `progress_percent`：0–100 的整数；
- `progress_message`：当前用户可读动作。

新增分析日志记录，每条包含：

- Job ID；
- 创建时间；
- 阶段；
- 日志级别（`info`、`warning`、`error`）；
- 用户可读消息。

日志仅追加，不保存请求体、响应体、密钥、Base URL 和异常堆栈。API 默认返回最近 20 条，避免响应无限增长。

## 后端流程

开始分析时根据视频时长和 30 秒切片长度计算总片段数，初始化进度。每个片段依次写入：

1. 开始生成代理片段；
2. 开始调用模型理解，并附带片段序号与时间范围；
3. 模型响应较慢需要重试时写入 warning；
4. 片段完成后增加 `progress_current` 并更新百分比。

所有日志与进度更新立即提交，使现有轮询能够读取。任务完成后写入完成日志并设置 100%；失败时写入经过脱敏的错误日志，保留已经完成的片段进度。

模型适配器通过可选的进度回调报告重试事件，不把 HTTP 或供应商内部细节传给页面。

## API

扩展现有 `GET /api/jobs/{job_id}`，增加：

- `progress_current`
- `progress_total`
- `progress_percent`
- `progress_message`
- `logs`：按时间升序排列的最近 20 条日志

不新增 SSE 或额外轮询接口，继续使用当前 Job 页面轮询机制，保持部署和 Cloudflare 配置不变。

## 前端

`JobProgress` 接收完整的进度信息。在 `understanding` 阶段：

- 高亮“理解视频内容”；
- 展示进度条、百分比、片段计数和当前动作；
- 展示可滚动的最近日志列表；
- warning 和 error 使用区别明确但不过度警示的颜色；
- 空日志时显示“正在准备视频理解”，避免空白区域。

页面继续按现有频率轮询。相同日志通过记录 ID 去重，避免视觉重复。

## 恢复、重试与异常

- 容器重启恢复任务时追加“任务已恢复，继续分析”日志，并基于持久化进度继续向用户显示状态。
- Job 手动重试时重置进度快照并保留旧日志，在新一轮开始前写入明显的重试分隔日志。
- 模型超时重试写 warning；达到最大次数后写 error，并让 Job 进入 failed。
- 日志写入失败不得掩盖原始分析错误，但应保持 Job 状态可落库。

## 测试与验收

后端测试覆盖：

- 片段总数与百分比计算；
- 每个关键节点的日志持久化；
- 模型重试日志；
- Job API 返回最近 20 条且顺序正确；
- 完成、失败和手动重试时的进度行为。

前端测试覆盖：

- understanding 阶段显示片段进度、百分比和当前消息；
- 日志级别与时间正确渲染；
- 无日志、失败和完成状态；
- 现有任务轮询与结果页流程不回归。

验收标准：长视频分析时，用户无需查看服务器日志即可知道当前处理片段、已完成比例、当前动作和是否正在重试；刷新页面后信息不丢失。
