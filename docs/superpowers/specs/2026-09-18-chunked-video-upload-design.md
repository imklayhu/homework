# Framewise 简化分片上传设计

## 背景与目标

Framewise 当前通过 Cloudflare Tunnel 暴露 Web 服务。局域网内单请求上传正常，但大视频经过 Cloudflare 时会受到单次请求体大小限制。系统需要在不改变 `3015` 端口、不公开额外服务端口、不引入对象存储的前提下支持最长课程视频上传。

本次实现简化分片上传：浏览器把视频切成固定大小的小请求，服务端暂存全部分片并在完成请求中合并，然后复用现有视频校验、持久化和分析任务创建流程。

## 范围

### 包含

- Web 默认使用 1 MiB 固定分片上传，以降低低速上行经 Cloudflare Tunnel 时触发 524 的风险。
- 分片串行发送，单片失败最多重试 3 次。
- 显示整体上传百分比和当前分片进度。
- 服务端初始化、分片写入和完成合并接口。
- 文件类型、声明大小、实际大小、分片数量和编号校验。
- 合并成功后创建现有 `Video` 与分析 `Job`。
- 保留原有 `POST /api/videos` 接口，兼容已有调用和测试。
- 成功、失败和重试埋点。

### 不包含

- 刷新页面后的断点续传。
- 暂停、继续或跨设备恢复。
- 多分片并行上传。
- OSS、S3 等对象存储直传。
- 内容哈希秒传或去重。

## 上传协议

### 1. 初始化

`POST /api/uploads/init`

请求：

```json
{
  "filename": "lesson.mp4",
  "content_type": "video/mp4",
  "size_bytes": 104857600,
  "chunk_size": 1048576,
  "total_chunks": 100
}
```

服务端校验：

- 扩展名与 MIME 类型属于 MP4、MOV 或 WebM。
- `size_bytes` 大于 0 且不超过 `MAX_UPLOAD_BYTES`（默认 300 MiB）。
- `chunk_size` 大于 0 且不超过 8 MiB。
- `total_chunks` 必须等于 `ceil(size_bytes / chunk_size)`。

成功返回 `201`：

```json
{
  "upload_id": "uuid",
  "chunk_size": 1048576,
  "total_chunks": 100
}
```

### 2. 上传分片

`PUT /api/uploads/{upload_id}/chunks/{index}`

- 请求体为原始二进制，不使用 multipart，降低额外开销。
- `index` 从 0 开始且必须小于 `total_chunks`。
- 非末片必须与声明的 `chunk_size` 完全一致；末片必须等于剩余字节数。
- 服务端先写入同目录临时文件，再原子替换为 `{index}.part`，避免中断留下看似完整的分片。
- 同一编号再次上传时安全覆盖，以支持前端单片重试。

成功返回 `204`。

### 3. 完成上传

`POST /api/uploads/{upload_id}/complete`

服务端执行：

1. 确认上传会话存在且尚未完成。
2. 确认所有分片存在且尺寸符合声明。
3. 按编号顺序流式合并，不把完整视频载入内存。
4. 校验合并后的实际字节数。
5. 复用现有媒体校验，检查格式和时长。
6. 将视频原子移动到 `data/uploads/{video_id}/source.{ext}`。
7. 在数据库事务中创建 `Video` 和分析 `Job`。
8. 提交后台分析任务，清理上传会话目录。

成功返回现有上传响应，HTTP 状态为 `202`：

```json
{
  "video_id": "uuid",
  "job_id": "uuid",
  "status": "uploaded"
}
```

## 服务端存储与状态

每次上传暂存在：

```text
data/tmp/chunk-uploads/{upload_id}/
├── manifest.json
├── 0.part
├── 1.part
└── ...
```

`manifest.json` 保存原始文件名、MIME、声明大小、分片大小、总片数与创建时间。上传会话不写入数据库，以保持 MVP 简单；完成接口通过目录和 manifest 恢复状态。

成功完成后删除该会话目录。失败时保留会话目录，便于同一页面内重试分片或完成请求。启动时和每次初始化时清理创建超过 24 小时的会话，避免临时文件无限增长。

## 前端流程

1. 沿用现有扩展名、MIME 和 300 MiB 前置校验。
2. 计算 `total_chunks = ceil(file.size / 1 MiB)` 并初始化会话。
3. 使用 `File.slice()` 串行上传每个分片。
4. 每片失败时等待 500 ms、1 s、2 s 后重试，最多共 3 次请求。
5. 每片成功后按已确认上传字节计算进度。
6. 全部分片完成后调用 complete。
7. complete 成功后沿用现有跳转，进入 `/jobs/{job_id}`。

上传中按钮禁用并显示：

```text
正在上传 48%（6/13）
```

任何阶段失败时显示可理解的错误信息；简化版本要求用户点击后重新开始整次上传，不实现刷新后的恢复。

## 错误处理

- `400`：元数据、分片编号、分片大小或文件内容非法。
- `404`：上传会话不存在或已被清理。
- `409`：分片不齐全、会话已完成或状态冲突。
- `413`：声明大小或实际合并大小超过限制。
- `500`：磁盘或其他未预期服务端错误；服务端记录 `upload_id` 和阶段，但不记录密钥。

服务端错误响应沿用 `{code, message}` 结构。前端保留最近一次明确错误，不把网络错误笼统显示成模型失败。

## 埋点

新增事件：

- `chunk_upload_started`
- `chunk_upload_chunk_retried`
- `chunk_upload_completed`
- `chunk_upload_failed`

事件属性仅包含文件大小区间、分片总数、失败阶段和错误码，不保存文件名或视频内容。

## 测试与验收

### API 自动化测试

- 初始化合法上传会话。
- 拒绝超过 300 MiB、非法格式和不一致分片数量。
- 接收完整分片并拒绝错误尺寸或越界编号。
- 重复上传同一分片可安全覆盖。
- 分片缺失时 complete 返回 `409`。
- 完整上传后按序合并、创建视频与任务并清理临时目录。
- 合并后大小不一致时不创建数据库记录。

### Web 自动化测试

- 1 MiB 以上文件被拆成正确数量的分片。
- 分片按顺序上传并在完成后调用 complete。
- 单片网络失败最多重试 3 次。
- 上传进度随成功分片更新。
- 最终失败会显示错误且不调用 complete。

### 部署验收

- 容器仍为 API 与 Web 两个，Web 继续监听宿主机 `3015`。
- 通过局域网与 Cloudflare Tunnel 分别上传一个超过 10 MiB 的有效视频。
- 两种入口均返回 `202` 并进入任务页。
- API 日志包含初始化、分片和完成请求，无 500。
- 原有单请求上传、管理员页面、分析与 Remix 流程继续通过。

## 安全与运维

- `upload_id` 使用不可预测 UUID。
- 所有路径由服务端生成，不使用用户文件名拼接路径。
- 合并采用流式读写，控制内存占用。
- 临时目录位于现有持久化 `data` 卷中，容器重建不会在上传过程中丢失已写分片。
- 不改变 Cloudflare Tunnel、宿主机端口或现有 `.env` 同步方式。
