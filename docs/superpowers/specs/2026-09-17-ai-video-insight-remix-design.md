# AI 视频理解与 Remix 工具：MVP 产品与技术设计

## 1. 项目背景

### 1.1 作业题目

完成并上线一个 Web 端视频解析工具，支持原生视频的内容理解、分析和 Remix。例如：从教育视频中提炼教学观点，并基于分析结果重新组织视频片段。

### 1.2 时间与交付约束

- 开发时间：最多 3 天。
- 交付形态：应呈现为完整产品，而不是单一脚本、聊天框或接口演示。
- 实现标准：核心主链路可以真实运行；非核心功能允许通过明确的产品边界延后。
- 部署方案：暂不锁定；架构应允许后续部署到 Vercel、Cloudflare、Railway、Render 或同类平台。
- 模型限制：允许使用 Gemini、OpenAI 等海外模型/API。

### 1.3 对 Remix 的明确解释

本项目中的 Remix 指：

> 根据视频分析得到的观点和时间段，由用户选择内容，系统对原视频片段进行智能选段、排序、裁剪、拼接，并导出一段新的短视频。

MVP 不包含生成式视频、数字人、复杂多轨时间线、镜头重绘或 AI 补帧。这些能力成本高、交付风险大，也不是验证“视频理解驱动再创作”闭环所必需。

## 2. 求职匹配度与作业策略

### 2.1 岗位重点

岗位强调：

1. Agent 产品全生命周期管理；
2. Agent Harness 能力与边界设计；
3. 市场与产品机会判断；
4. 独立完成 Demo 设计、部署、验收和上线；
5. AI 产品理解和创新能力。

### 2.2 候选人优势映射

简历中的相关优势：

- 有 4 款独立产品从需求、设计、开发到上线的闭环经历；
- 有 Agent 编排、RAG、STT/TTS、Human-in-the-loop 和 badcase 复盘经验；
- 能独立完成 Next.js、FastAPI、PostgreSQL、Docker、CI/CD 等工程落地；
- 有 IELTS Agent 教育场景经验，容易说明“教学观点”的产品价值；
- 有模型成本、计量、配额和商业化设计经验。

### 2.3 本作业应展示什么

该作业不应只展示“调用模型总结视频”，而应主动展示：

- 对用户问题的定义：看完长视频、找到重点、制作可传播片段的成本高；
- 对模型能力边界的理解：ASR 擅长稳定时间轴，多模态模型擅长联合理解画面与语言，两者组合比单一路径可靠；
- 对 Agent Harness 的理解：阶段化编排、结构化输出、校验、重试、降级和人工确认；
- 对评测的理解：观点不是越多越好，应评估真实性、覆盖率、时间戳准确度和片段完整性；
- 对产品化的理解：上传、状态反馈、播放器联动、分析结果和导出构成完整闭环。

## 3. 产品定位

### 3.1 一句话定位

面向课程创作者和知识型视频用户的 AI Video Studio：上传视频后，自动识别章节与核心观点，并把选中的观点剪成可下载的短视频。

### 3.2 目标用户

MVP 只聚焦一类用户：

- 有录播课、访谈、知识分享视频的内容创作者、课程运营或学习者；
- 视频以单人讲解、访谈、PPT/屏幕演示为主；
- 需要快速复盘内容，或制作 30–90 秒的传播片段。

### 3.3 核心用户任务

用户希望：

1. 不完整看完视频也能理解其结构和主要观点；
2. 点击观点即可回到对应原视频证据；
3. 选择重要观点后快速产出一段连贯短视频；
4. 对 AI 选择有控制权，避免错误内容直接发布。

### 3.4 成功标准

MVP 的成功不是支持最多格式，而是完成以下闭环：

> 上传一个 3–15 分钟教育视频 → 获得可验证的结构化分析 → 选择观点 → 生成并下载 Remix 视频。

验收指标：

- 10 分钟以内测试视频解析成功率达到 90% 以上；
- 章节和观点均可跳转至对应时间段；
- 核心观点均有原文或视觉证据，避免无依据总结；
- Remix 片段边界误差控制在约 2 秒内；
- 10 分钟视频在正常 API 条件下 3 分钟左右返回分析结果；
- 导出的 Remix 可以正常播放且音画同步。

## 4. 方案比较与决策

### 4.1 方案 A：只分析转写文本

流程：视频提取音轨 → ASR → LLM 总结 → FFmpeg 裁剪。

优点：最快、最便宜、时间戳稳定。

缺点：不属于真正的原生视频理解；无法利用 PPT、板书、代码演示、动作等视觉信息。答辩时很容易被追问“和播客总结工具有什么区别”。

结论：不采用为主方案，仅作为视频模型失败时的降级路径。

### 4.2 方案 B：视频完全交给多模态模型

流程：上传原视频 → 多模态模型直接输出观点和时间戳 → FFmpeg 裁剪。

优点：链路短，容易展示原生视频理解。

缺点：长视频推理耗时和费用较高；模型给出的时间戳可能漂移；重新上传大文件会增加失败成本；难以稳定控制输出。

结论：不建议在 3 天 MVP 中单独使用。

### 4.3 方案 C：混合多模态流水线（推荐）

流程：

1. ASR 产生稳定的分段文本和时间戳；
2. 对视频抽取关键帧或将短视频直接交给原生视频模型；
3. 将转写、关键帧/视频理解结果交给分析 Agent；
4. 结构化输出章节、观点、证据和推荐片段；
5. 用户确认后由 FFmpeg 裁剪和拼接。

优势：

- 同时满足原生视频理解与可靠时间轴；
- 可以标记证据来自语音、画面或两者；
- 任一多模态步骤失败时仍能退化为转写分析；
- 能体现 Agent Harness 的编排、边界、校验与降级能力。

决策：MVP 采用方案 C。

## 5. MVP 功能范围

### 5.1 P0：必须真实可用

#### 上传与样例

- 支持 MP4；若时间允许再支持 MOV/WebM；
- 限制最长 15 分钟、最大 300 MB；
- 提供一个已验证的教育类样例视频；
- 上传前明确显示大小、时长和格式限制。

#### 任务状态

- 展示真实阶段，而非伪造百分比：上传、预处理、转写、视觉理解、洞察生成、完成；
- 支持失败提示和重新分析；
- 刷新页面后能够恢复任务状态。

#### 视频理解与分析

- 一句话摘要；
- 3–5 个核心教学观点；
- 3–8 个章节及时间范围；
- 每个观点包含标题、解释、证据、开始/结束时间、证据类型、置信度；
- 点击章节或观点可控制播放器跳转；
- 对视觉证据使用“画面”标签，对语音证据使用“转写”标签。

#### Remix

- 勾选 1–3 个观点；
- 自动按原视频顺序排列，也允许上移/下移；
- 展示预计成片时长；
- 调用 FFmpeg 裁剪并拼接；
- 生成 30–90 秒 MP4，允许预览和下载。

### 5.2 P1：有余力再做

- 用户编辑观点标题；
- 导出字幕文件 SRT；
- Remix 烧录简易字幕；
- 16:9 与 9:16 两种导出比例；
- 分析结果复制为 Markdown；
- 任务历史记录。

### 5.3 明确不做

- 登录、计费、多租户权限；
- YouTube/Bilibili 链接抓取；
- 复杂视频编辑器；
- 生成式 B-roll、数字人或语音克隆；
- 多人实时协作；
- 无限制长度和格式；
- 大规模生产级队列和自动扩缩容。

这些能力可写入 Roadmap，但不能占用三天 MVP 的主链路时间。

## 6. 信息架构与交互设计

### 6.1 页面结构

MVP 采用单页工作台，避免路由和账户系统消耗时间。

#### 初始态

- 左上：产品名称和一句价值主张；
- 中心：拖拽上传区；
- 下方：支持格式、时长、隐私提示；
- 辅助入口：“试用示例视频”。

#### 处理中

- 左侧：视频预览和文件信息；
- 右侧：分阶段状态列表；
- 显示已完成阶段和当前阶段；
- 允许终止或重新开始失败任务。

#### 结果态

- 左栏：固定视频播放器；
- 右栏：`概览 / 章节 / 核心观点 / Remix` 四个页签；
- 点击任何带时间戳的结果，播放器跳转并高亮当前内容；
- 页面底部或侧栏展示处理耗时和本次估算成本，体现产品经理的成本意识。

### 6.2 Remix 交互

1. 在观点卡片点击“加入 Remix”；
2. Remix 面板显示片段列表；
3. 默认按原视频时间排序；
4. 用户可删除或调整顺序；
5. 显示总时长，超过 90 秒时给出限制提示；
6. 点击“生成视频”；
7. 生成完成后展示播放器和下载按钮。

### 6.3 人机协同设计

- AI 只负责推荐观点和候选片段；
- 用户负责最终选段和顺序确认；
- 低置信度观点显示提示，不自动进入 Remix；
- 输出前允许用户试听/预览原片段；
- 不将模型生成的标题直接永久写入原视频。

## 7. 技术架构

### 7.1 推荐技术栈

#### Web 前端

- Next.js + TypeScript；
- Tailwind CSS 或现有组件库；
- 原生 HTML5 Video；
- 轮询任务状态，MVP 不引入 WebSocket。

#### API 与任务编排

优先采用 Python FastAPI，因为视频、FFmpeg 和媒体元数据处理更顺手；若希望减少项目数量，也可全部使用 Next.js API Route，但长任务不适合部署在严格 Serverless 超时环境。

- FastAPI：上传、任务状态、分析结果、Remix 请求；
- BackgroundTasks 或单独 worker：MVP 任务执行；
- Redis + Celery/RQ：只在部署环境需要跨进程可靠任务时引入；
- Pydantic：约束模型结构化输出。

#### 媒体处理

- FFmpeg/ffprobe：音轨提取、元数据读取、片段裁剪、拼接、转码；
- 关键帧策略：每 20–30 秒抽一帧，并在 ASR 章节边界附近补帧；
- MVP 采用重新编码保证不同片段可稳定拼接，不追求零拷贝极致速度。

#### 存储

- 本地开发：本地磁盘；
- 部署：Cloudflare R2、S3 或兼容对象存储；
- 数据库：SQLite 用于单机演示，部署时切换 PostgreSQL/Supabase；
- 文件设置自动过期，例如 24 小时后删除。

### 7.2 模型建议

#### 最终模型组合（2026-09-17 核验）

| 环节 | 默认模型/工具 | 角色 | 选择原因 |
|---|---|---|---|
| 原生视频理解 | `gemini-3.8-flash` | 理解视频画面、语音语义、PPT/板书、章节和视觉证据 | 当前稳定 Flash 模型；支持 Text、Image、Video、Audio、PDF 输入，支持结构化输出和 Agentic Video Understanding |
| 时间轴转写 | `whisper-1` | 输出 segment/word 级转写与时间戳 | OpenAI 官方文档明确说明 `timestamp_granularities[]` 仅由 `whisper-1` 支持，适合视频剪辑所需的精确时间轴 |
| 洞察生成 | `gemini-3.8-flash` | 合并视频观察与 ASR 时间轴，生成章节、观点、证据和候选片段 JSON | 复用主模型，减少三天 MVP 的 SDK、密钥和错误处理复杂度；原生支持结构化输出 |
| JSON 修复 | `gemini-3.8-flash` | 只在 Schema 校验失败时修复输出 | 不增加第三个模型；最多修复一次，防止无限重试 |
| 视频裁剪与拼接 | FFmpeg | 按确定时间戳完成 Remix | 属于确定性媒体处理，不需要也不应调用生成模型 |

#### 主模型调用方式

`gemini-3.8-flash` 通过 Gemini File API 接收视频。File API 适合大于 100 MB、10 分钟以上或需要在多次请求中复用的视频；MVP 上传限制为 15 分钟、300 MB，因此不应将视频编码成 Base64 直接塞入请求。

视频处理建议：

- 默认使用 Agentic Video Understanding，让模型动态浏览长视频并选择所需的转写、画面和音频信息；
- 要求模型输出视觉观察、章节候选、关键事件和对应 `MM:SS` 时间点；
- Gemini 时间点只作为语义定位，不直接作为最终剪辑边界；
- 最终 `start_ms/end_ms` 应对齐 `whisper-1` 的 segment/word 时间戳并经过范围校验；
- 如果 Agentic 模式出现延迟或接口不稳定，降级为 Static 模式；短视频可使用默认 1 FPS，成本敏感时可将采样率调整为 0.5 FPS。

#### 为什么 ASR 使用 `whisper-1`

OpenAI 当前更推荐 `gpt-transcribe` 处理一般录音转写，`gpt-4o-mini-transcribe` 也可用于成本敏感的纯文本转写；但本产品的核心任务包含按语句边界裁剪视频，需要 segment 或 word 级时间戳。官方文档说明 `timestamp_granularities[]` 只支持 `whisper-1`，因此 MVP 应优先保证时间轴可用性。

建议请求参数：

```json
{
  "model": "whisper-1",
  "response_format": "verbose_json",
  "timestamp_granularities": ["segment", "word"]
}
```

如果后续评测发现专业术语识别明显影响体验，可采用双层策略：用 `gpt-transcribe` 生成高质量文本，用 `whisper-1` 生成时间轴，再进行文本对齐。但三天 MVP 不建议默认开启双 ASR，因为它会增加费用、延迟和对齐复杂度。

#### 模型备选与降级

- `gemini-2.5-flash`：兼容性备选，仅在当前项目账号无法访问 `gemini-3.8-flash` 时启用；
- `gemini-3.8-flash` Static 模式：Agentic 视频处理不可用时的第一降级；
- 关键帧 + `gemini-3.8-flash`：原视频上传或处理失败时的第二降级；
- `whisper-1` 纯转写分析：多模态模型失败时仍返回章节和观点，但 UI 必须标记“视觉分析暂不可用”；
- 不在默认链路中接入 Pro 模型。只有评测证明 Flash 在特定复杂视频上持续失败时，才考虑对低置信度任务路由到更强模型。

#### 国产成本优先方案（Homework 推荐）

如果优先考虑成本、国内访问和账号管理复杂度，可以将默认方案替换为阿里云百炼单云组合：

| 环节 | 国产模型/工具 | 作用 | 成本与取舍 |
|---|---|---|---|
| 原生视频理解 | `qwen3-vl-flash` | 分析视频画面、PPT、板书、演示动作和章节 | 北京地域输入价格低，且有新用户 Token 额度；适合 MVP 主链路 |
| 结构化洞察 | `qwen3-vl-flash` | 生成摘要、章节、观点、证据与候选片段 JSON | 复用同一模型，减少供应商和 SDK 数量 |
| 可选转写 | `qwen3-asr-flash-2026-02-10` | 生成中文转写文本 | ON_DEMAND 已开放；官方资料未确认句级/词级时间戳，因此不承担精确切点职责 |
| 高质量兜底 | `qwen3-vl-plus` | 只处理 Flash 低置信度或结构复杂的视频 | 单价明显高于 Flash，不进入默认调用链路 |
| Remix | FFmpeg | 裁剪、排序、拼接和导出 MP4 | 确定性处理，无模型费用 |

推荐默认配置：

```text
AI_PROVIDER=dashscope
VIDEO_UNDERSTANDING_MODEL=qwen3-vl-flash
INSIGHT_MODEL=qwen3-vl-flash
TRANSCRIPTION_MODEL=qwen3-asr-flash-2026-02-10
FALLBACK_VIDEO_MODEL=qwen3-vl-plus
```

选择该组合的原因：

- 只需要一个阿里云百炼账号和 API Key；
- 中文教育视频的转写和语义理解更符合主要演示场景；
- `qwen3-vl-flash` 与 `qwen3-vl-plus` 可以通过相同 Adapter 切换；
- `qwen3-asr-flash-2026-02-10` 可通过 ON_DEMAND 调用，官方参考价约为北京 ¥0.00022/秒，10 分钟约 ¥0.132；
- `qwen3-vl-flash` 当前提供 100 万 Token 新用户额度，Homework 调试通常可以被额度覆盖；
- 即使超出免费额度，单次短视频分析也容易控制在角级成本。

建议将国产方案作为实际开发默认值，将 Gemini + Whisper 作为架构文档中的国际模型对照方案。这样既能证明模型选型能力，也能避免为了一个 Homework 同时维护两家海外 API。

注意事项：

- ON_DEMAND `/models` 已确认包含 `qwen3-vl-flash`、`qwen3-vl-plus` 和 `qwen3-asr-flash-2026-02-10`，但不包含 `paraformer-v2`；
- `qwen3-vl-flash` 已通过真实公网 MP4 探针，能够理解画面并返回时间点；
- MVP 以 Qwen VL 返回的候选时间范围定位，首尾增加 1–1.5 秒缓冲并由用户预览确认；
- 若真实教育视频评测发现切点明显不稳定，再增加本地 `faster-whisper` 生成 segment/word 时间轴；
- 原工作空间中已实测可理解视频的 `qwen3.8-flash` 仅作为端点异常备选；
- 免费额度、地域和价格可能调整，上线前以百炼控制台实际账单为准。

#### 模型配置原则

模型名称不得散落在业务代码中，应通过环境变量集中配置：

```text
VIDEO_UNDERSTANDING_MODEL=gemini-3.8-flash
INSIGHT_MODEL=gemini-3.8-flash
TRANSCRIPTION_MODEL=whisper-1
VIDEO_PROCESSING_MODE=agentic
```

每次任务记录实际模型版本、处理模式、Prompt 版本、Token/音频用量、耗时和估算费用，便于演示成本意识并支持 badcase 回溯。

#### 官方能力依据

- Gemini 3.8 Flash 模型页：<https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash>
- Gemini 视频理解与 File API：<https://ai.google.dev/gemini-api/docs/video-understanding>
- OpenAI Speech-to-text 指南：<https://developers.openai.com/api/docs/guides/speech-to-text>
- OpenAI `whisper-1` 模型页：<https://developers.openai.com/api/docs/models/whisper-1>

#### 为什么不在 MVP 中本地部署模型

- 三天内 GPU、模型权重、显存和推理环境会占用大量时间；
- 作业评估的是产品判断与落地闭环，不是训练或部署基础模型；
- API 更适合快速量化单次成本和展示模型降级策略。

### 7.3 逻辑架构

```text
Browser
  ├─ Upload / Player / Insight UI / Remix UI
  │
  ▼
FastAPI
  ├─ Video API
  ├─ Job API
  ├─ Insight API
  └─ Remix API

  ▼
```

## 8. 核心处理流程

### 8.1 上传与预检

1. 前端检查扩展名和文件大小；
2. 服务端再次检查 MIME、大小和时长；
3. ffprobe 获取时长、分辨率、编码、音轨信息；
4. 创建 Job，状态为 `uploaded`；
5. 保存源视频，开始后台任务。

### 8.2 媒体预处理

1. 提取单声道低码率音频供 ASR；
2. 按固定间隔与潜在章节边界提取关键帧；
3. 对超高分辨率视频生成分析代理文件，降低上传模型的成本；
4. 更新阶段为 `preprocessed`。

### 8.3 转写

ASR 输出按句或短段切分：

```json
{
  "start_ms": 12500,
  "end_ms": 18900,
  "text": "今天我们讲三个判断用户需求的方法。"
}
```

保留精确时间戳；若无有效音轨，不直接失败，而是进入视觉分析降级路径。

### 8.4 原生视频理解

输入：视频或关键帧、视频基本信息，以及任务指令。

输出重点：

- 屏幕/PPT/板书中出现的主题；
- 演示步骤、代码、图表或动作；
- 画面变化对应的章节边界；
- 语音未明确表达但画面提供的信息；
- 不尝试由视觉模型独立生成最终精确时间戳。

### 8.5 洞察 Agent

将转写与视觉观察对齐，生成严格 JSON：

```json
{
  "summary": "视频介绍了通过用户访谈、行为数据和小实验验证需求的方法。",
  "chapters": [
    {
      "title": "为什么不能只听用户表达",
      "start_ms": 20000,
      "end_ms": 145000,
      "summary": "区分用户说什么和实际做什么。"
    }
  ],
  "insights": [
    {
      "id": "insight_01",
      "title": "行为证据比口头意愿更可靠",
      "explanation": "用户表达会受到情境影响，应使用行为数据交叉验证。",
      "start_ms": 48000,
      "end_ms": 76000,
      "transcript_evidence": "不要只问用户会不会买，要看他是否愿意付出成本。",
      "visual_evidence": "PPT 对比了 Say 与 Do 两列。",
      "evidence_types": ["transcript", "visual"],
      "confidence": 0.91,
      "remix_reason": "观点完整、开头明确，适合独立传播。"
    }
  ]
}
```

### 8.6 自动校验

在结果进入 UI 前执行确定性校验：

- JSON Schema/Pydantic 校验；
- `0 <= start_ms < end_ms <= video_duration`；
- 观点数量、章节数量和单片段时长限制；
- transcript evidence 必须能在相邻 ASR 文本中找到或达到语义相似阈值；
- 片段边界前后增加 0.5–1.5 秒缓冲，减少切断语句；
- 时间段重叠过多时合并或标记；
- 校验失败只重试分析步骤，不重新上传和转写视频。

### 8.7 Remix 渲染

1. 接收用户选中的 insight id 和排序；
2. 从数据库读取可信时间段，不接受前端任意文件路径；
3. 为片段应用合理边界缓冲；
4. 使用 FFmpeg 统一编码参数；
5. 按用户顺序拼接；
6. 输出 MP4，并保存时长、大小和下载地址；
7. 渲染失败允许重试，不重复执行视频分析。

## 10. Agent Harness 设计

### 10.1 Harness 的组成

- 明确任务阶段和状态；
- 模型输入裁剪与上下文组装；
- JSON Schema 约束；
- 输出校验与有限次数重试；
- Prompt 和模型版本记录；
- Token、音频时长、视频时长与费用记录；
- 超时、限流、服务失败的降级；
- 用户最终确认位；
- 可复现的测试样例和 badcase 记录。

### 10.2 重试原则

- 网络错误、429、5xx：指数退避，最多 2–3 次；
- Schema 错误：携带错误信息进行一次修复请求；
- 业务事实错误：不通过盲目重试解决，而通过证据约束与人工确认解决；
- FFmpeg 渲染失败：保留输入片段和日志，允许单独重试。

### 10.3 降级顺序

1. 视频原生理解 + ASR；
2. 关键帧理解 + ASR；
3. 仅 ASR 分析，并在 UI 明确标记“视觉分析暂不可用”；
4. ASR 失败但画面可读时，提供视觉摘要，不开放高置信度 Remix；
5. 均失败时保留文件并允许重新分析。

## 11. 异常、安全与隐私

### 11.1 用户可理解的错误

- 视频超过 15 分钟；
- 文件过大或格式不支持；
- 视频没有有效音轨；
- 视频损坏或无法解码；
- 模型服务暂时不可用；
- 分析结果不足以生成可信观点；
- Remix 超过 90 秒；
- 导出失败。

### 11.2 安全控制

- 不直接信任文件扩展名；
- 随机化存储 key，禁止使用用户文件名作为服务器路径；
- FFmpeg 参数使用参数数组，不拼接用户输入的 shell 命令；
- 下载使用短时效签名 URL；
- 限制上传体积、时长和并发；
- 日志中不保存完整视频和 API Key；
- 使用环境变量管理密钥；
- 文件默认 24 小时后删除，并在 UI 明示。

### 11.3 内容边界

- MVP 不承诺事实核查，只承诺基于上传视频提取和重组；
- 对观点提供证据和时间戳；
- 不声称模型判断等同于专业结论；
- 如果用于公开发布，用户必须拥有视频内容的使用权。

## 12. 评测与验收方案

### 12.1 最小测试集

准备 5 类短视频，每类 3–8 分钟：

1. 单人正对镜头讲课；
2. PPT + 旁白；
3. 屏幕操作/代码教学；
4. 双人访谈；
5. 无语音或弱语音的视觉演示。

其中选择一个稳定样例作为现场 Demo。

### 12.2 分析指标

| 指标 | 定义 | MVP 目标 |
|---|---|---:|
| 观点真实性 | 观点能被视频证据支持的比例 | ≥ 90% |
| 核心内容覆盖 | 人工标注核心观点被识别的比例 | ≥ 80% |
| 时间戳准确 | 起点落在人工边界 ±2 秒内 | ≥ 80% |
| 章节合理性 | 章节无明显重复、断裂 | ≥ 80% |
| 视觉增益 | 至少一条有效洞察来自画面而非转写 | 目标样例必须满足 |
| 片段完整性 | Remix 不明显切断首尾语句 | ≥ 90% |
| 任务成功率 | 限制内视频完成主链路 | ≥ 90% |

### 12.3 评测方式

- 人工先为样例视频标记章节、观点和时间范围；
- 将模型输出与人工标注对照；
- 用 0/1 或 1–5 分简单打分，不搭建复杂评测平台；
- 记录 badcase、原因、解决方案和是否进入 MVP；
- 保存 prompt_version 与 model_version，保证结果可追踪。

### 12.4 必测负向用例

- 超限文件；
- 损坏视频；
- 没有音轨；
- 模型返回非 JSON；
- 模型时间戳越界；
- 选中片段总长超过上限；
- FFmpeg 失败；
- 页面刷新后恢复任务；
- API Key 未配置。

## 13. 成本估算

### 13.1 成本口径

精确 API 单价会随模型和地区变化，因此产品中应按下面的可配置公式计算，而不是将某个单价硬编码在 UI：

```text
单次成本 = ASR 音频分钟成本
         + 视频/图片模型输入成本
         + 分析模型输入输出 Token 成本
         + 存储与下行流量成本
         + Remix 计算成本
```

### 13.2 单个 10 分钟视频的估算

以下按当前选择的 ON_DEMAND 国产模型链路估算，不作为供应商报价：

| 项目 | 低位估算 | 高位估算 | 说明 |
|---|---:|---:|---|
| `qwen3-vl-flash` 视频理解与结构化输出 | ¥0.01 | ¥0.25 | 取决于采样率、视频 Token、输出长度以及是否拆成两次调用 |
| `qwen3-asr-flash-2026-02-10` | ¥0.132 | ¥0.132 | 按北京参考价 ¥0.00022/秒 × 600 秒；MVP 可关闭 |
| 本地临时文件与 FFmpeg | ¥0 | <¥0.01 | Homework 在本机运行，暂不计部署计算和对象存储 |
| **不启用独立 ASR** | **约 ¥0.01** | **约 ¥0.25** | 由 VL 模型给出候选时间段 |
| **启用独立 ASR** | **约 ¥0.14** | **约 ¥0.39** | ASR 主要用于补充转写文本，不能假定具有精确时间戳 |

为覆盖一次失败重试或较长输出，演示预算可按 **¥0.50/条 10 分钟视频** 管理。30 分钟视频可先按 3 倍线性估算，但最终应以接口返回的 usage 为准。

注：实际实现前应将选定模型官网的最新价格填入配置表，用 3 个真实样例记录供应商返回的 usage，得到实测成本。对于面试作业，“展示计算方法和实测结果”比声称一个永远准确的固定数字更可信。

### 13.3 开发与演示期现金成本

假设三天内执行 30–80 次 10 分钟等价的完整调用：

- 不启用独立 ASR：理论模型成本约 ¥0.3–¥20；
- 全部启用独立 ASR：理论模型成本约 ¥4.2–¥31.2；
- 实际开发通常会使用 1–3 分钟短样例并复用已分析结果，因此建议准备 **¥10–¥20 API 余额**；
- 新账号免费额度有效时，实际现金支出可能接近 ¥0；
- 本次暂不考虑部署，本地存储、数据库和 FFmpeg 不产生新增现金成本。

如果使用国产成本优先组合（`qwen3-vl-flash + 可选 qwen3-asr-flash`）：

- 10 分钟 ASR 参考价约 ¥0.132；若仅用视频模型生成候选时间范围，可不产生这笔费用；
- 视频理解与结构化输出按 Token 计费，建议在未实测前为 10 分钟视频预留约 ¥0.01–¥0.25；
- 单个 10 分钟视频约 ¥0.01–¥0.25（无 ASR），或约 ¥0.14–¥0.39（有 ASR）；
- 新账号免费额度有效时，Homework 开发与演示的模型现金支出很可能接近 ¥0；
- 仍建议充值 ¥10–¥20 或确认账户可按量计费，避免演示时因额度、欠费或地域配置中断。

### 13.4 产品化后的成本控制

- 限制视频时长、分辨率和文件大小；
- 对分析使用低码率代理视频；
- 固定间隔抽帧，在章节边界才补帧；
- 对同一视频内容哈希去重，避免重复分析；
- 分离分析与 Remix，重新导出不重复调用模型；
- 失败只重跑失败阶段；
- 文件自动过期；
- 免费版限制分钟数，付费版按视频分钟计量；
- 使用更强模型只处理低置信度样例，而不是全量调用。

## 15. 演示与答辩设计

### 15.1 3 分钟演示脚本

1. **问题（20 秒）**：长教育视频复盘和二次剪辑都很耗时；
2. **上传（20 秒）**：展示格式边界、样例视频和真实处理阶段；
3. **理解（60 秒）**：展示摘要、章节、观点、视觉证据，点击时间戳回看；
4. **Remix（50 秒）**：选择观点、调整顺序、生成并播放短视频；
5. **产品判断（30 秒）**：说明为什么采用 ASR + 视频模型、为什么保留人工确认、为什么没有做生成式视频。

### 15.2 必备兜底

- 内置已分析完成的示例任务；
- 保留真实上传入口，避免被认为是静态 Demo；
- 录制完整主链路视频；
- 模型失败时仍可展示已保存结果；
- README 给出本地启动方式、测试账号（若有）、支持范围和已知限制。

### 15.3 评委可能追问

#### 为什么不是只做字幕总结？

回答：字幕无法理解 PPT、代码、板书和演示动作。本方案使用视觉证据增强语义理解，同时用 ASR 保证时间轴可靠。

#### 为什么不把整段视频一次性丢给模型？

回答：单次多模态调用简单，但时间戳、重试成本和可控性不足。将转写、视觉理解、结构化分析分离，更容易校验、降级和替换模型。

#### AI 剪错怎么办？

回答：AI 只推荐，用户确认后才生成；每个观点展示证据与原视频跳转；时间戳经过范围校验并添加边界缓冲。

#### 如何规模化？

回答：将后台任务迁移到队列 Worker；对象存储直传；任务幂等；按内容哈希缓存；模型分层；按视频分钟计量；增加并发和配额控制。

#### 怎么收费？

回答：按处理分钟数比按文件数合理。免费体验提供少量分钟；个人版提供月度分钟包；团队版增加共享素材库、模板和批量任务。

## 17. 最终建议

1. 将项目名称、视觉和文案做成真正的内容工作台，而不是“AI Demo”；
2. 核心卖点应是“有证据、可跳转、可重组”，不是生成一段泛泛的摘要；
3. 第一天下午之前优先验证模型时间戳与 FFmpeg 裁剪，尽早暴露最大风险；
4. 不做登录、支付和复杂编辑器，三天全部围绕一条完整主链路；
5. 在页面或答辩中展示真实耗时、模型版本和估算成本；
6. 准备稳定样例、已完成任务和录屏三层演示兜底；
7. 把 badcase、降级路径和人工确认当作 Agent 产品能力来展示，而不是隐藏模型限制。

这套方案的完成度与候选人的简历叙事一致：能从用户问题出发，设计 Agent Harness，理解模型边界，以有限成本独立完成可上线产品闭环。
